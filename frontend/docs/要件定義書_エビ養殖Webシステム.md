## 1. プロジェクト概要

- **システム概要**：IoTセンサー・データ分析を用いたインドネシアエビ養殖場向け階層型（本社／現場養殖場長）統合管理Webシステム
- **対象企業・対象養殖池の概要**：インドネシア国内に複数のエステート（各エステート内に数十〜数百の池）を有するエビ養殖企業。本社は都市部（ジャカルタ等）、養殖現場は地方に分散
- **背景**：広大な土地に分散する複数ファームの状況をリアルタイムに把握できず、異常発生時の経営インパクトの見積もりや、収穫タイミング・出荷計画の精度確保が困難な状況にある

---

## 2. 現状の課題（As-Is）

- **現在の養殖管理業務の流れ**：現場で目視・簡易測定によるモニタリングを実施し、状況を管理棟・本社へ報告する体制（デジタル連携は未整備）
- **現状の記録方法とその問題点**：
  - 広大な土地に分散するファームの状況がリアルタイムで把握できない
  - 現場ごとの報告精度・運用状況にばらつきがあり、出荷計画の精度が安定しない
  - 現場データ（給餌・死亡・水質・成長）が経営判断に使える形に整理されておらず、収穫タイミングや出荷計画の判断が経験則に依存している
- **過去に発生した問題とその原因の仮説**：
  - 水質悪化（DO低下等）の予兆に本社・現場双方が気づくのが遅れ、対応が後手に回る
  - 本社側が各ファームの詳細状況を把握できず、異常時・収穫時期の経営判断が遅れる
- **現地スタッフのITリテラシー・言語・通信インフラ状況**：
  - 通信インフラはLoRaWAN／4G／5Gを想定するが、現場環境によっては通信断絶のリスクがある



## 3. システム化の目的・ゴール

- **システム化の目的**：現場IoTセンサー・日次入力・週次サンプリングから得られるデータを、本社と現場養殖場長それぞれに必要な粒度・形式（本社＝分析結果、現場＝詳細データ）に整理して提供し、全社レベルでの経営判断と現場レベルでの迅速な異常対応を両立させる
- **達成すべきゴール**：
  - 本社が全国のファームの状態を一目で把握し、閾値超過や異常が発生したファームにすぐ気づける状態の実現
  - 本社が池ごとの収穫推奨タイミング・利益予測、生物学的リスクの状態、将来の出荷可能量を分析結果として確認できる状態の実現
  - 現場養殖場長が自ファームのIoTデバイスからの詳細な数値を確認し、閾値超過アラートを受け取って迅速に対応できる状態の実現
  - 現場で得られるIoTデータの変化をAIが学習・予測し、現場養殖場長の判断を助けるアドバイスを提示できる状態の実現
  - 現場養殖場長が日々の池の状態（生存数・死亡数・天候等）および週次サンプリング結果を報告できる仕組みを整える
  - 閾値超過等の条件に応じてアクチュエーター（ポンプ・エアレーション等）を自動制御し、現場養殖場長が遠隔から状態監視・承認・オーバーライドできる状態の実現

## 4. スコープ定義

### 4.1 対象範囲（In Scope）
- 本社統合ダッシュボード（全ファームの状態一覧、サマリー表示）
- 本社向け分析結果表示（収益最適化、生物学的リスク、先行営業・将来在庫予測の3領域）
- 分析結果から元データへのドリルダウン機能
- 現場養殖場長向けモニタリング画面（自ファーム内の池ごとのIoT詳細データ確認、閾値超過アラート受信）
- 3〜5分間隔でのIoTセンサーデータ収集
- 閾値超過に基づくアラート機能
- 日次報告書の入力機能（現場養殖場長）
- 週次サンプリング・ラボ検査結果の入力機能、および関連KPI（ABW・ADG・SR・Biomass・FCR・COGS等）の自動算出
- IoTデータの変化を学習したAIによる予測・アドバイス提示機能（現場養殖場長向け）
- アクチュエーター（ポンプ・エアレーション等）に対する自動制御機能（PID制御・Safety Layer）、および現場養殖場長による監視・承認・オーバーライド機能

### 5.2 対象外範囲（Out of Scope）
- 現場作業員による端末からのシステム操作（本システムでは対象外。物理作業自体は従来通り現場養殖場長の指示のもとオフラインで実施）
- 疾病発生確率等、確度の高い予測の提示（十分な学習データ・検証が整うまでは対象外。詳細は17章のフェーズ方針を参照）
- （記入：例）加工工場内の生産管理システムとの直接連携
- （記入：例）輸出通関・物流管理機能

### 5.3 フェーズ分け
- **Phase 1**：ルールベースのKPI算出・収益シミュレーション・将来在庫予測（まず「見える化・説明可能性」を確立）
- **Phase 2**：異常検知・生物学的リスクスコアの導入（十分な履歴データが蓄積された段階で検証）
- **Phase 3**：機械学習による予測の高度化（モデル方式はデータ量・精度検証結果を踏まえて選定）

## 6. 前提条件・制約条件

- **前提条件**：
  - 各池に防水型IoTセンサー（スマートプローブ）が設置され、DO・pH・水温・濁度・TDS・水位等が自動計測されていること
  - 各池にポンプ・エアレーション等のアクチュエーターが設置され、システムからの制御信号を受けられること
  - 週次サンプリング（体重測定・尾数計測）およびラボ検査（ビブリオ菌・PCR検査等）が現場運用として実施されること
- **技術的制約**：
  - 通信はLoRaWAN／4G／5Gを想定するが、現場によっては通信断絶が発生し得る
  - 3〜5分間隔の連続データ送信に耐えうる通信・サーバー設計が必要
- **法規制・データ主権**：インドネシア国内の個人情報保護法（PDP法）、データの越境移転可否の確認が必要
- **言語**：現場養殖場長向けはインドネシア語必須、本社向けはインドネシア語／英語併記を想定
- **開発体制**：開発チームは2名。設計・実装・検証はAgentic SDLC（後述17章）に基づき、AIエージェントを活用して進める想定
- **想定インフラ**：クラウド基盤としてGCP（Google Cloud Platform）を想定。センサーデータはEdge経由でGCPへ送信される構成を前提とする
- **業務ルールの確定が必要な項目**：利益の定義（粗利／営業利益等）、市場価格の更新ルール、収穫判断の優先順位、リスク閾値、AIが推奨してよい範囲、供給予測の扱い（予測値か安全余裕を見た販売可能量か）等は、企業側との合意により確定する（詳細は15章参照）

## 7. 用語定義

| LoRaWAN | 低消費電力・長距離通信規格。現場センサーの通信に使用 |

| AI予測アドバイス | 現場のIoTデータ・数値変化の履歴をAIが学習し、今後の傾向予測や対応の提案を現場養殖場長に提示する機能 |

| Safety Layer | 自動制御が誤作動した場合にも安全を確保するための制御層 |

## 9. 業務要件（To-Be業務フロー）

1. 各ファームの池に設置された防水型IoTセンサーが3〜5分間隔でDO・pH・水温・濁度・TDS・水位等を自動測定し、LoRaWAN／4G／5G経由でシステムに送信する
2. 現場養殖場長が日次で給餌量・死亡回収数・エサ残り具合・業務日報等を入力し、週次でサンプリング（尾数・総重量）およびラボ検査結果（ビブリオ菌・PCR等）を入力する
3. システムが日次データ・週次データ・IoTデータをもとに、養殖KPI（ABW・ADG・SR・Biomass・FCR・COGS等）を自動算出するとともに、閾値超過の判定を行い、超過があればアラートを生成する
4. あらかじめ設定されたルール（PID制御・Safety Layer）に基づき、必要に応じてポンプ・エアレーション等のアクチュエーターを自動制御する
5. **現場養殖場長**：自ファームのモニタリング画面で、池ごとの詳細な数値および自動制御の動作状況をリアルタイムに確認できる。閾値超過時にはアラートを受け取り、詳細数値を確認したうえで自動制御の承認、または手動介入（Human Override）を判断する
6. **AIサポート**：蓄積されたIoTデータ・KPIの変化をAIが学習し、今後の水質変化・成長傾向の予測や対応方針を現場養殖場長に対してアドバイスとして提示する
7. システムが算出したKPI・アラートをもとに、収益最適化（収穫推奨日・利益予測）、生物学的リスク（健康スコア・危険度・要因・推奨アクション）、先行営業・将来在庫予測（出荷可能時期・サイズ別供給量）の3つの分析結果を生成する
8. **本社統括エグゼクティブ**：全社ダッシュボードで全ファームの状態と分析結果（3領域のサマリー）を確認する。気になる池があれば分析結果から元データへドリルダウンし、必要に応じて該当ファームの現場養殖場長に確認・指示を行う

## 11. データ要件

- **収集データ項目（IoT）**：DO（溶存酸素）、pH、水温、濁度、TDS、水位
- **収集データ項目（日次入力）**：給餌量、死亡回収数、エサ残り具合、業務日報等
- **収集データ項目（週次サンプリング・ラボ）**：サンプリング尾数、合計重量、ビブリオ菌数、PCR検査結果等
- **データ取得方法**：IoTは自動取得、日次・週次データは現場養殖場長による入力
- **データ粒度・頻度**：IoTは3〜5分間隔、日次データは1日1回、週次データは週1回程度
- **データの見え方の違い**：
  - 現場養殖場長：自ファームの全池について、IoT・日次・週次の詳細データをそのまま確認可能

## 17. 開発体制・進め方（Agentic SDLC）

> システム設計書（ShrimpOS Agentic SDLC 基本設計）に基づく、本システムの開発体制・進め方の要点

- **開発チーム規模**：2名
- **基本方針**：Humanが「何を・なぜ作るか」を決定し、AIエージェントが「どう実現するか」を担当する。ただし重要な意思決定はHumanが承認する
- **エージェント構成**：

| Agent | 役割 |
|---|---|
| Management Agent | 全体管理・タスクの振り分け・進行状況の管理 |
| Design Agent | 要件整理・システム設計・API／DB／UI設計 |
| Data/ML Agent | IoTデータ設計・特徴量設計・MLモデル設計・評価 |
| Builder Agent | ソースコード・インフラ・MLパイプラインの実装 |
| Verify Agent | 実装・設計・MLモデルの独立した検証 |

- **基本フロー**：Human → Management Agent → Design Agent／Data-ML Agent → Builder Agent → Verify Agent → Human（最終承認）
- **Humanによる承認が必要な事項**：
  - システム設計（Architecture）の変更
  - 重要なDB／API変更
  - MLモデルの本番採用
  - 自動制御ルールの導入
  - 本番環境への重要な変更
- **本要件定義書との関係**：本書（要件定義書）はDesign Agentの入力・成果物の一つと位置づけられ、今後の設計変更はこの要件定義書の更新とHumanの承認を経て反映される想定
